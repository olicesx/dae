## 目标
上一个提交 `c09d1535f` 把 `udp-ordered-dispatcher` 从默认特性中移除，注释说"等 end-to-end QUIC 和 proxy-dial benchmarks 建立 SLO 后重新启用"。本次推进补齐这两类缺失的 benchmark，跑出 ordered vs legacy 的对比数据，再根据数据决定是否把 `udp-ordered-dispatcher` 加回 `defaultSemanticRefactorFeatures()`。SLO 形式为纯测量型（遵循 dae 现有 benchmark 全是测量型的惯例），不内置硬阈值。

## 复用现有设施（不新造轮子）
全部已在探索阶段确认存在且可复用：
- `udpReuseSimulationConn` / `newCountingProxyEndpointDialer` / `newFactoryProxyEndpointDialer`（`udp_reuse_simulation_test.go:27,148,169`）—— 内存态 transport stub + 计数 dialer，避免真实 socket

- `runProducers` / `udpDispatcherBenchmarkKeys` / `udpDispatcherBenchmarkKeyIndex`（已有 helper）

## 计划改动

### 1. 新增 `control/udp_quic_e2e_bench_test.go`（核心交付物）
端到端 QUIC benchmark，镜像 `TestQuicInitial_FlowsThroughBothNewDispatchers` 的全链路但改为测量型：

**`BenchmarkQuicInitialEndToEnd_*`** —— 两个对照实现，用 `b.Run` 两级命名（参照 `BenchmarkUDPOrderedDispatcherSubmitDrain:62-73` 的 `legacy_pool` / `new_dispatcher` 命名风格）：
- `BenchmarkQuicInitialEndToEnd/legacy_pool`：`cp.udpOrderedDispatcher = nil`（fallback 到 `DefaultUdpTaskPool.EmitTask`），`cp.udpReplyDispatcher = nil`（走 legacy per-endpoint replySender）
- `BenchmarkQuicInitialEndToEnd/ordered_ingress`：`cp.udpOrderedDispatcher = newDefaultUDPOrderedDispatcher()`，`cp.udpReplyDispatcher = newDefaultUDPReplyDispatcher()`

每个 b.N 迭代：
1. 生成一个新 flow key（不同 src port，避免命中既有 endpoint cache，从而每次都走完整的 dial+write 路径）
2. `cp.submitOrderedUDPIngress(key, task, discard)`，task 闭包内调 `cp.handlePkt(...)`
3. 等 task 完成（用 `sync.WaitGroup` 或原子计数器做 barrier，放在 timed 区内，参照 `runBoundedUDPDispatcherBenchmark:140`）
4. 每迭代做 endpoint teardown：`ue.Close()` + 在 goroutine 里 `ue.replyRuntime.tasks.Wait()`（带超时，参照回归测试 `:544-577`，防止 reply WG ticket 跨迭代泄漏）

子 case 维度：`flows`（单流 vs 多流）、`producers`（1 vs 8）。

**关键正确性**：`setupQuicInitialRegressionTestState` 只在 setup 时调一次；timed 区内每迭代只调轻量 reset（`DefaultUdpEndpointPool.Reset()` + `DefaultAnyfromPool.Reset()`）或用 factory dialer 每迭代新建 conn。避免全局池爆掉。

### 2. 新增 `control/udp_proxy_dial_bench_test.go`
proxy-dial 成本 benchmark，隔离 dial+write 而非 scheduler：

**`BenchmarkUdpProxyDial_*`** —— 两种对照：
- 直接 `DefaultUdpEndpointPool.GetOrCreate(key, &UdpEndpointOptions{GetDialOption: ..., Handler: ...})`，用 `newCountingProxyEndpointDialer`
- 同样两个变体：`createAdmission = nil`（无 admission gate） vs `createAdmission = dispatcher.acquireEndpointCreateAdmission`（有 ordered dispatcher 的冷启动 admission）

测量每次 `GetOrCreate` cache-miss 的 `DialContext`+`WriteTo` 成本（用计数器验证每次都真的 dial 了），以及 cache-hit 的纯 lookup 成本。子 case：`cache=miss` / `cache=hit`。

### 3. 验证 & 跑对比数据
```bash
go test -tags=dae_stub_ebpf -run '^$' -bench 'BenchmarkQuicInitialEndToEnd|BenchmarkUdpProxyDial' -benchmem -benchtime=2s ./control/
go test -tags=dae_stub_ebpf ./control/ ./cmd/   # 确保不破坏现有测试
go vet -tags=dae_stub_ebpf ./control/...
```
对比 `legacy_pool` vs `ordered_ingress` 的 ns/op 和 allocs/op。**决策点**：若 ordered 不显著劣于 legacy（同一数量级、allocs 不更多），则继续步骤 4 重新启用；否则保留 opt-in，在结果里说明原因。

### 4. （条件性）重新启用默认 —— 仅当步骤 3 数据支持
修改 `cmd/semantic_refactor_features.go:30-34`：把 `control.SemanticRefactorFeatureUDPOrderedDispatcher` 加回 `defaultSemanticRefactorFeatures()`，更新注释（从"opt-in until benchmarks establish SLOs"改为说明 benchmark 已验证）。
同步更新 `cmd/semantic_refactor_features_test.go:14-27` 的 `TestDefaultSemanticRefactorFeaturesKeepsOrderedIngressOptIn`（重命名+改期望为两个特性都在）。

### 5. 提交
按 AGENTS.md 的 semantic commit 规范，例如：
`test(control): add end-to-end QUIC and proxy-dial dispatcher benchmarks`（+ 若启用默认则拆分或合并为 `feat(control): re-enable udp-ordered-dispatcher by default`）。

## 风险与缓解
- **flaky/泄漏**：reply dispatcher 的 tasks WG 跨迭代泄漏会让 bench 卡住——严格按回归测试 `:544-577` 的 goroutine+超时 Wait 模式
- **全局池污染**：`setupQuicInitialRegressionTestState` 的 swap+restore 必须在 `b.Cleanup` 里完整还原，否则污染同进程其他测试
- **构建状态**：当前 `trace` tag 下 build 有预存在的 eBPF 生成问题（`bpfRoutingEpochIp` undefined），与本次无关；所有验证用 `-tags=dae_stub_ebpf`

## 不在范围内
- 不改 scheduler 本体逻辑（`udp_ordered_dispatcher.go` / `udp_reply_dispatcher.go`）
- 不动 eBPF 生成问题
- 不改生产路径 `control_plane.go` 的 Serve 循环
